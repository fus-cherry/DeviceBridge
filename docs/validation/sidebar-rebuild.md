# 0.1.7 sidebar repair candidate

This is a repair of the approved 0.1.7 sidebar, not a new feature release.

## Reproduced from production code

- ADB `device`, paired CoreDevice and HDC `Connected` produce `candidate` routes.
  Inventory intentionally considers these discoverable/authorized routes, but the
  old sidebar required `available`, hiding normally discovered phones before selection.
- A previous failed check also permanently moved a still-detected device into the
  collapsed group. It is now retained as an advisory while a new explicit check is offered.
- Inventory was already polled every five seconds. Replacing its timer was not the fix.
  Added tests exercise the real timer and status changes rather than a separate test-only loop.
- Selected-session disappearance/reappearance could leave old healthy presentation
  blocking a same-device reselect. Inventory must invalidate readiness, never auto-connect.
- The generic maintenance flag also covers iOS content helpers. Only the actual
  Android maintenance controller may own separate route-health transitions.
- Selection now atomically checks that the route captured for the readiness probe
  is still the preferred authorized route before committing it. A successful old
  route probe cannot mark a replacement route ready. Timestamp-only observations
  are allowed; authorization, route identifiers and routing metadata must match.

## Interface

- A scrollable sidebar with uniform card rows and fixed icon/status columns.
- `Detected devices` means eligible for a connection check, not verified feature readiness.
- Offline/unauthorized routes remain available in a separate collapsible section.
- Section and help headers use full-width buttons. Clicking text or whitespace
  toggles the section, not just the small chevron. Long identifiers are truncated
  and long device names wrap within the sidebar column.
- Background discovery does not block row clicks with a modal spinner.

## Validation contract

1. Portable Swift tests run actual production parser/inventory/presentation and session code.
   The portable harness is not a macOS build.
2. `check-workspace-inventory.sh` compiles the real macOS view model and exercises the
   real five-second poll, offline/authorization recovery, selection failure/retry,
   removal/reappearance and route replacement with synthetic command boundaries.
3. Three targeted macOS XCTest cases launch the real SwiftUI app with inventories
   generated by the production parsers. They click header text/whitespace repeatedly,
   select a device, check automatic regrouping without pressing Refresh, assert
   row bounds against the sidebar header (not the whole window), and save English
   and Chinese screenshots. These run only on an isolated GitHub-hosted runner.
4. Existing full protocol, secure-channel, core, workspace-flow and packaging checks
   remain enabled. A successful source-string check is not a behavior/UI pass.
5. The final report must name the exact tested commit and any failed/unrun stages.

## Limits

No user-local checkout or physical phone is accessed. Synthetic UI success does not
prove USB authorization, vendor firmware, real HDC/ADB transport, or real-device
content operations. The build is ad-hoc signed and not Apple-notarized until a
separately authorized signing setup succeeds. No main merge or public release is
part of this repair.

## First macOS UI loop

The full core and workspace checks passed. The first UI run saved a real screenshot
showing an unrelated macOS local-network permission dialog for Python from earlier
loopback contract tests. The auto-regroup check ran, but the two following UI launches
could not expose controls, so the build correctly failed and produced no DMG. No
permission was granted and no privacy setting was changed. The UI phase now runs
before those network checks, and tests use the standard New Window command when
macOS does not restore a test window. A fresh successful interaction run is required.

## Multi-window lifecycle boundary

The shared WindowGroup model now retains idempotent workspace host tokens. Closing
one window no longer calls global stop while another window still owns discovery.
A production-timer model regression covers repeated attach/detach and reopening;
the UI auto-recovery test opens and closes a second real window before changing
its synthetic transport to online. This is a verified code-path risk, not evidence
that multiple windows caused the user's original report.

## Second macOS UI loop

The isolated UI phase removed the unrelated permission-dialog interference. Automatic
regrouping passed again. The Chinese layout test exposed cross-process fixture
preferences not being loaded; fixture language now enters the app's normal localization
path in its own process. The long-name test found the row's accessibility identifier was
not exposed as expected while child elements had their own identifiers. Rows now expose
one explicitly labelled button with a selected trait, and every failed assertion retains
the current AX hierarchy. These checks must run again; their failures were not waived.

## Third macOS UI loop

The two-window close and final-window reopen flow passed on the actual runner. The
Chinese language assertion also passed. The retained AX hierarchy pinpointed why
the long-row query still failed: an identifier on the passive section-content VStack
propagated to all child device buttons, overriding their unique identifiers. That
container identifier has been removed; per-device identifiers and labels remain.
The full-row interaction assertions remain enabled for the next run.
